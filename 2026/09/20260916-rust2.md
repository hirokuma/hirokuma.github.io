なんだこの間が抜けたタイトルは。。。

こういう感じのプログラムがあったとしよう。  
ポイントは、モジュールaの構造体`A`が別モジュールbをフィールドに持っていて、外部に対してはモジュールbを見せるつもりがない、というところか。
そのためaの中で`pub use`して`B`を持ってきている。

```rust
# b.rs
pub struct B {
    pub y: i32,
}
```

```rust
# a.rs
pub use crate::b::B;

pub struct A {
    pub x: i32,
    pub b: B,
}
```

```rust
# main.rs
mod a;
mod b;

use a::{A, B};

fn main() {
    let a = A {
        x: 5,
        b: B { y: 10 },
    };
    println!("a.x: {}, a.b.y: {}", a.x, a.b.y);
}
```

これ自体は特に問題ではない。別モジュールmainからは`B`もモジュールaの持ち物であるかのようにアクセスできる。

## flutter_rust_bridgeは対象のrsファイルしか見ない

最近扱っているFlutterでflutter_rust_bridgeを使っている。  
Rustの部分はcargo workspaceにして複数プロジェクトある。
`flutter_rust_bridge.yaml`の`rust_root`に書いたパスのモジュールの`rust_input`にあるクレートをFlutterから参照できるようにしているのだと思う。

先程調べたが、`flutter_rust_bridge.yaml`は`flutter_rust_bridge_codegen`の引数で指定できるようで複数持つことも可能なので自由度はあるようだ。
が、少なくとも今回は1つのアプリがworkspaceのクレートを使う構造なので`flutter_rust_bridge.yaml`も1つだ。

Flutterアプリから直接扱わせたいのは先ほどのモジュールaだ。`main`もそういう感じで作っているので想像はつくだろう。  
なのでもし`flutter_rust_bridge_codegen`を使った場合、Flutterから見える対象になるのはモジュールaの内容だけである。  
`struct B`については`pub use`しているがモジュールaの中にはないのでFlutterからは中身が見えない`RustOpaqueInterface`として見える。
それだとアプリから`struct B`の中身にアクセスできないのだ。

これに突き当たったとき、面倒なのでモジュールaの中にsetter/getterを`impl A`として作って隠すようにした。
これはこれで動かないことはなさそうだったが、Rustの関数はFlutterからは`async`で見えるようになるのでいちいちめんどくさい。
効率が悪そう。気持ち悪い。

じゃあ`struct B`をモジュールaに持っていったとすると、モジュールbがモジュールaの`struct B`を`use`しないといけなくなる。
この例だと`struct`しかないファイルなので分かりづらいが、モジュールaが`use b`してモジュールbが`use a`するともちもちになるというか循環参照になるというか、そういうのはダメなんじゃないの？と思ったのだ。

[Gemini](https://share.gemini.google/0qBwIo56e2JK)に聞くと問題ないらしい。
もちろん関数の再帰呼び出しになるような関係はダメだが`use`しあうこと自体は言語仕様にもあるらしい。  
そうなんだ。。。

で、でも、同格の相手ではなく上下関係があるなら相互で参照するのは避けたいという気持ちがある。

## そういうときはトレイト

どうしても解決できなかったのでAIに聞いたところ、

* 下側でsetterインターフェースを持つトレイトを用意
* 上側で`struct`本体とそこへのsetterを実装する

そうすると、`flutter_rust_bridge_codegen`が見る上側には`struct`のコードが入っているし、下側はそれを直接参照しないし、ということで循環が起きないそうだ。
