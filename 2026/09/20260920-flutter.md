## cargo workspaceでもよい

新規作成したflutter_rust_bridgeのプロジェクトでは`rust/`の直下にプロジェクトが1つという構成である。
これは1つでないとダメということはなく、cargo workspaceにしてもよい。  
`Cargo.toml`の内容はまねしておいたほうが無難だと思う。

```toml
[package]
name = "rust_lib_app1"
version = "0.1.0"
edition = "2021"

[lib]
crate-type = ["cdylib", "staticlib"]

[dependencies]
flutter_rust_bridge = "=2.13.0"

[lints.rust]
unexpected_cfgs = { level = "warn", check-cfg = ['cfg(frb_expand)'] }
```

`flutter_rust_bridge.yaml`はこうなっているが、これも変更可能である。
cargo workspaceにした場合はどのプロジェクトをベースにするか`rust_root`で指定する必要がある。  
`rust_input`はコンマで複数指定できるそうだ。`lib.rs`から`pub mod`でたどれないとダメらしい。

```yaml
rust_input: crate::api
rust_root: rust/
dart_output: lib/src/rust
```

### コードの変更

自作したRustプロジェクトを持ってくる場合には変更がいるだろう。  
さきほどの`lib.rs`からたどれないといけないのもあるが、自動生成されたコードも`mod`で取り込まないといけない。

```rust
pub mod api;
mod frb_generated;
```

また、`api`モジュールにはこういうコードがあった。
これをFlutter側での`await RustLib.init()`で呼び出すようだ。

```rust
#[flutter_rust_bridge::frb(init)]
pub fn init_app() {
    // Default utilities - feel free to customize
    flutter_rust_bridge::setup_default_user_utils();
}
```

初期化したいことがあればそこに埋め込んでおくと良さそう。  
AndroidではRustの`log`クレートならログ出力に出してくれていたが`setup_default_user_utils()`の後でないとダメそうだ。
`flutter_rust_bridge`にfeaturesを足しておかねば出てこないと思う。

```toml
[dependencies]
flutter_rust_bridge = { version = "=2.13.0", features = ["log"] }
```

`log`クレートはログ出力本体ではないのでそこに流し込むことができればなんでもよい。
もちろん`tracing`でもよい。

```toml
tracing = {version = "0.1.44", features = ["log"]}
```

Rustでは同期関数でも、何もしなかったらFlutterでは非同期関数として呼び出されるようになる。
flutter_rust_bridgeのデフォルトプロジェクトではサンプルの`greet()`に`#[frb(sync)]`を付けて同期にしている。
Flutter側で単に`Text()`で表示したいだけなのに`async`だったりすると面倒になるようだ。

* [Synchronous Dart - flutter_rust_bridge](https://cjycode.com/flutter_rust_bridge/guides/concurrency/sync-dart)

### 各プラットフォーム向けの変更

先ほどまでの変更はRustについてだったが、`rust_root`の変更はAndroidやiOSなどの各プラットフォームのビルドスクリプトにも修正が必要だった。  
Androidについては`rust_builder/android/build.gradle`の変更が必要で、そうしないと"Missing package section"でデバッグ実行時にエラーになった。  
たとえば`rust/`から`"rust"/api/`になったとするとこうなった。

```gradle
cargokit {
    // 変更前は "../../rust"
    manifestDir = "../../rust/api"
    libname = "rust_lib_app1"
}
```

iOSは`rust_builder/ios/rust_lib_app1.podspec`の変更になるらしい。
今回iOSは見ていなかったのだがAI氏がそういうのでそうなんだろう。

```podspec
    :script => 'sh "$PODS_TARGET_SRCROOT/../cargokit/build_pod.sh" ../../rust/api rust_lib_app1',
```

### cargo workspaceでなくてもよい

cargo workspaceとそうでない場合の違いは、cargo workspaceだと「このディレクトリ以下でひとまとまり」みたいなのがわかりやすいのと、
トップの`Cargo.toml`に書いた`[workspace.dependencies]`をその下で参照することでバージョン管理しやすくすることくらいだと思う。  
気にすべきは`rust_root`のプロジェクトがRustでビルドできるかどうかだ。

## おそらく別crateに属するものは返せない

Flutter/Dart側で直接扱うことが出来ないオブジェクトは`RustOpaqueInterface`として扱われる。
引数としては使えるがフィールドを参照したりメソッドを呼び出したりはできない。

```rust
abstract class Hogee implements RustOpaqueInterface {}
```

`rust_root`にあるコードはだいたいDartにも変換されてそうやって扱えるのだが、
`Cargo.toml`で参照しているような自分のcrateにはないコードだとworkspace内であっても変換されないようだ。

`flutter_rust_bridge_codegen generate`はデフォルトでカレントディレクトリの`flutter_rust_bridge.yaml`を参照するというだけで、指定すればそれを参照する。

```text
      --config-file <CONFIG_FILE>
          Path to a YAML config file.
          
          If present, other options and flags will be ignored. Accepts the same options as the CLI, but uses snake_case keys.
```

`dart_output`を同じところにしてしまうとファイルを上書きしてしまう。
つまりRustで扱っていたものがさらに増える、というよりは新たに追加してそれぞれ扱えるようになるというだけであろう。

今やろうとしてたのが、`enum`が別のcrateにあるので参照できなかったからDartで呼び出せるようにしてみたいな、くらいなものだったので、
それをやるにしてはちょっと壮大過ぎると思ったのだ。  
ただこちらにも書いたが、`Cargo.toml`を挟んだ循環参照にはできないので、別crateにある値を返すだけというメソッドは扱えないのだ。

### newtypeで逃げられる？

トレイトもそうだが、こういうのはnewtypeというかタプル構造体というか、そういうので回避できたのでここでもできるんじゃなかろうか？  
おそらくそうではない。  
参照できればOKなのであれば`pub use`で宣言すれば済むはずだが、それではダメだったのだ。
Rustのオリジナルコードはビルドできるが自動生成した`rust/api/src/frb_generated.rs`がエラーになるのは直接定義したコードがそこにないときである。

ではnewtypeは？  一応は直接定義したコードはそこにあることになる。そこにないのはタプルになった型の実装だ。
なのでそれは先ほどのルール通り`RustOpaqueInterface`として扱われる。詳しく確認していないが、`struct`の中に`pub`でないフィールドがあったりプリミティブではなくコードもそこにない型を含んでいたらそうなると思う。

しかしnewtypeは`impl`でそこに実装を持ち込むことができる。そのコードはそこに存在するのでFlutter/Dartからも呼び出すことができる。
格好は悪いが`impl`で呼び出したいメソッドを全部中継して呼び出せば済ませられそうだ。

### mirror

`frb(mirror)`というマクロを使うことで、flutter_rust_bridgeで対象にしていないクレートにある`struct`や`enum`を擬似的に対象としているクレートに持ってくるようなことができる。
あくまで「疑似的」に過ぎず、そんなに便利なものではない。私が使ったのは`enum`だけだったのだけど、ちょっと思っているのと違ったというところだ。

* [External types - flutter_rust_bridge](https://cjycode.com/flutter_rust_bridge/guides/third-party/manual/external-types)

こういう感じでflutter_rust_bridgeで対象にしているRustファイルの中に書いておくと、Flutter/Dartに対しては`_DummyName`を見せず(たぶん)に`OriginalName`としてコードを展開する。
その展開するコードはもちろんflutter_rust_bridgeで対象しているRustファイルの中になくてはならない。  
なんというか、メソッドとしては戻り値の方は`OriginalName`の方なのだけど、Flutter/Dartで扱うときには`_DummyName`の実装を`OriginalName`という名前で扱えるようになっている、といえばよいか。

```rust
#[flutter_rust_bridge::frb(mirror(OriginalName))]
pub enum _DummyName {
  ......
```

一番のネックは、結局はコードがなくてはならないというところだろう。
だいたいはコピーして持ってくることになるか。
なのでもう1つのネックはオリジナルのコードが変更になると`frb(mirror)`の方も変更しないといけないし手動でやらないといけないというところだろう。  
`enum`の場合はコンパイルエラーが起きないような変更(順番が変わるとか間に追加されるとか)をしやすいので、整合が取れていないことに気づきにくいかもしれない。

Dart側では小文字始まりのキャメルに変換されている。元が`AbcStart`だったら`abcStart`になるような変換だ。

## どうFlutterたちと付き合うか

おそらくflutter_rust_bridgeを使いたい場合、Rustの方が高速だとか、元々Rustで作っていたけどモバイルで使いたいとかではなかろうか。
UIだけFlutterを借りてきて計算をRust側で行うとか。そういう感じだと頻繁にRust側を呼び出すよりも、UI側で必要な情報をまとめてRustを呼び出すなどして行き来を少なくしたいか、
行き来が多くてパフォーマンスが悪くなってもそれほど気にならないとかではなかろうか。  
そうじゃなかったら、AndroidはKotlinを、iOSはSwiftを使って直接実装すればよいと思う。
AIでの実装がまともになってきているならそっちの方が変なことに悩まなくて済みそうな気がする。
ネイティブ言語よりRustの方が高速ということだったらわからんが、どちらもコンパイルするならそうでもないのでは？ KotlinはJVM経由してるんだったらちょっと落ちるのか？

それでも、クロスプラットフォームを挟むという怖さを減らしたいという気持ちはあると思う。
OSは安全だったけど使ってるプラットフォームがハッキングされてダメになりました、とか。  
やっぱり間に挟まるもの(自分の力が及ばないもの)は少なければ少ないほどよいのだ。

それならお前はなんで今からFlutterを始めたんだ、と言われると、AIをそこまで自在に使えるような気がしないからだ。
便利だから調べ物だったり、わからないコードを書いてもらったりするが、自分が期待するものを指示してちゃんと実装してもらえるという自信がまったくない。
やろうとも思ってなくて、そういうのは他力本願だ。早く技術的に枯れて私でも使えるようになってくれと期待している。

かといって待っていると仕事がなくなってしまうのでね。
