C言語で、ポインタだけ使いまわして、pthreadなどで使うので必要に応じてmutexするというやり方がある。
あれのRust版は`Arc<Mutex<T>>`だろう。
"A"がつかない`Rc`もあるが、だいたいそういうことをしたいときは非同期処理なので`Arc`の方で良いと思う。

## mut

つくっていたプログラムが、非同期ではあるものの処理は並列させないので参照だけ最初に作って関数に渡していたのだが、
毎回同じ引数を与えるのでなんか嫌になって`struct`によく使う引数だけまとめることにした。
ちょっと違うけどこういうイメージ。

```rust
struct Params<'a> {
  pub db: &'a Db,
  pub btc: &'a mut BtcWallet,
  pub eth: &'a mut EthWallet,
}
```

元が参照だったので、そのまま参照を使った。

その辺までは良かったのだが、機能部が大きく複数に分かれていたので`impl`で名前が重なるのも面倒だから`struct ParamA`と`struct ParamB`のように分けることにした。
そこもまだ良かったのだが、同じ関数の中で`ParamA`と`ParamB`を使う必要が出てきた。

`Params`の各フィールドだけ最初に作っておき、必要に応じて`ParamA`や`ParamB`のインスタンスを作ってメソッドを実行していたのだが、
`mut`があるので2つインスタンスを作ろうとすると「もう`mut`されてる」みたいなエラーになってしまう。  
面倒だったので、結局`ParamA`と`ParamB`をまとめて`Params`に戻して、メソッド名の衝突はサフィックスを付けるなどして逃げた。

このとき`Arc<T>`で回避しようとしたのだが、`mut`があるなら`Arc<Mutex<T>>`じゃないとダメだ、ということになった。
エラーになるからわかるのだが、

## moveしている例

これはダメな例で、`&`ではなくそのまま使っているので2つ目の`v2`はエラーになる。

```rust
struct Params {
    pub a: String,
    pub b: String,
}

struct ParaParams {
    pub p: Params,
}

fn print_params(v: &ParaParams) {
    println!("a: {}, b: {}", v.p.a, v.p.b);
}

fn main() {
    let p = Params {
        a: "Hello".into(),
        b: "World".into(),
    };
    let v = ParaParams {p};
    let v2 = ParaParams {p}; // ★moveしているのでエラー
    print_params(&v);
    print_params(&v2);
}
```

これはOKだ。

```rust
struct Params {
    pub a: String,
    pub b: String,
}

struct ParaParams<'a> {
    pub p: &'a Params,
}

fn print_params(v: &ParaParams) {
    println!("a: {}, b: {}", v.p.a, v.p.b);
}

fn main() {
    let p = Params {
        a: "Hello".into(),
        b: "World".into(),
    };
    let v = ParaParams {p: &p};
    let v2 = ParaParams {p: &p};
    print_params(&v);
    print_params(&v2);
}
```

## Arc は参照カウントするやつ

[Arc](https://doc.rust-lang.org/std/sync/struct.Arc.html)は Atomically Reference Counted の略だそうだ。  
atomically なら`Mutex`は内蔵してるんじゃないのと思ったが、変更できるような可変参照(mutable reference)はデフォルトでは提供しないらしい。
非同期でそうしたいなら`Mutex`などのatomicなやつを併用するよう書いてある。
まあ、そういう仕様なら仕方ないですな。`get_mut`は共有向きではないということだろう。redbの取得でもそういう名前のメソッドがあったと思う。

## tokioでのMutex

非同期の処理を作る場合、今のところtokioのやつしか使ったことがない。  
あそこでもtokio、ここでもtokio、なんでもかんでもtokio。
tokioに依存しすぎていて怖い。。。

それで`Mutex`だが、[std::sync::Mutex](https://doc.rust-lang.org/std/sync/struct.Mutex.html)もあるし[tokio::sync::Mutex](https://docs.rs/tokio/latest/tokio/sync/struct.Mutex.html)もある。
`tokio::spawn()`などを使っているので`Mutex`もtokioの方を使っていたのだが、Geminiに質問すると「原則として std::sync::Mutex を使い、await を跨ぐ場合のみ tokio::sync::Mutex を使います」などと言われた。  
それは本当なの？と疑うのは悪くないだろう。

確かにtokioの方の`Mutex`の文章にも、一般に言われているのとは反対にstd::sync::Mutexを非同期コードで使うのはOKだし普通だ、違いは`.await`をまたいでロックできることだ、というようなことが書かれている。
書かれているよな？ 英語力には自信がないのだが翻訳がそういっているので文字通り受け止めよう。Geminiが言っているとおりだ。

しかし`async`の関数で`.await`をまたがないことはほとんどないのではなかろうか。
設計を巧みにやれば回避できるのかもしれないが、私にはできるような気がしない。
そもそも、呼び出したいメソッドが`async fn`だったら`.await`を使うことになるので自動的に`tokio::sync::Mutex`になるはずだ。  
ただ、`T`が単に値を入れる箱だったり`async`メソッドを全く持たないようであれば`std::sync::Mutex`でよさそうだ。

どうやら比較的シンプルな`std::sync::Mutex`とタスクをまたぐ`tokio::sync::Mutex`ではパフォーマンスがかなり違うらしい。
なので、データアクセスのところは`std::sync::Mutex`にして取り出したり書き込んだりするだけにして、`async`はそこと切り離すとよいよ、ということだった。

## むずかしそう

とはいえ、ねぇ。。。
データとメソッドがセットになってるから楽なのであって、切り離すと面倒じゃなかろうか。
`T`が`async`ではないメソッドしかないのであればよいのだが、使っているクレートが`async fn`メソッドだったら連鎖して`async`になってしまうのでどうしようもないのか。
stdとtokioの`Mutex`を混在させることもできないので、1つでも`async`メソッドを呼び出すようであればtokioの方を使うしかない。

むずかしそうなので、将来の私に期待しておこう。
