最近LDKをちょっと触っていたのだが、自分のアプリにLNノード機能を持たせずに外部のLNノードを操作するだけでも良いのでは？と思い始めた。
いくらライブラリで扱いやすくなったとしても、そもそもLNノードの運用自体が非常にめんどくさい。
それなら単体アプリに任せてしまえばいいのだ。まあ、自分がLNノードになったほうが自由度が高いのは間違いないのだがね。

## LNノード

Linuxのアプリとして動かしやすいLNノードはこれらだろう。

* ACINQのEclair or phoenixd
* BlockstreamのCore-Lightning(c-lightning)
* LightningLabsのlnd

どれがよいとか悪いとかは特にない。

## lndはgRPC

今回はlndにする。  
[Nigiri](https://blog.hirokuma.work/bitcoin/01_basics/regtest.html#nigiri)で`nigiri start --ln`とすればCore-Lightningとlndが立ち上がるのでそれを使う。
[Polar](https://blog.hirokuma.work/bitcoin/01_basics/regtest.html#polar)はGUI操作できて直感的だしわかりやすいのでそちらもありだろう。

## Rustで扱う

RustでgRPCを扱おうとすると[grpc-rust](https://grpc.io/docs/languages/rust/quickstart/)になるようだ。
リポジトリ名はそうなのだが、クレート名は`tonic`だ。

protoファイルを使えば取り込みやすいのかもしれないが、誰かやってるならそれを使いたい。  
lndの場合はtonic_lndがメジャーなようだったがここ3年ほどリリースされていない。
[docs.rs](https://docs.rs/releases/search?query=tonic_lnd)だと2026年8月5日に更新されているようだがリリースバージョンは2023年3月11日のv0.5.1が最後だ。

ではfedimint版かvoltage版かで迷ったが、今回は[voltage版](https://docs.rs/voltage-tonic-lnd/latest/voltage_tonic_lnd/)にしよう。
voltage版はfedimint版をベースにしているようなので、なにかやりたいことがあったのだろう。

なんにしても、ここの部分はgRPCを扱いたいというだけで、ここに処理本体があるわけではない。
型定義がほとんどだ。

## lndのtls.certはwebpkiが受け付けない

サンプルに`getinfo` APIを動かすコードがあったので試したのだが、CERTファイル関係で実行時にエラーが起きる。

```log
Tonic(tonic::transport::Error(Transport, ConnectError(Custom { kind: InvalidData, error: InvalidCertificate(Other(OtherError(CaUsedAsEndEntity))) })))
```

Claudeさん(無料)に聞いたところ、こんな感じだった。
webpkiは悪くない、ということか。

* lndの`tls.cert`はサーバ証明書とCA証明書を兼ねたファイルになっている
* rustl(webpki)は兼用したファイルは許容しない(`CaUsedAsEndEntity`)
  * 「CAとして発行された証明書を、サーバの身元証明に使ってはいけない」という規則
  * [Error WebPKIError(CAUsedAsEndEntity) - The Rust Programming Language Forum](https://users.rust-lang.org/t/error-webpkierror-causedasendentity/48162)
* lndやREST APIでエラーにならないのは、そういうチェックをしてないからじゃないかな

lndのissueを探すとまだOPENのものが残っていた。そうなのねー。

* [Self-signed TLS certificates don't work with rustls · Issue #5450 · lightningnetwork/lnd](https://github.com/lightningnetwork/lnd/issues/5450)

lndが作った`tls.cert`は使わず、自作してCAとサーバ証明書を分けてlndには作った方を使わせるのがよいようだ。
`tls.key`や`tls.cert`はlndの起動時になければ作る、期限が切れたら作る、みたいな動きをするので、最初から作っておけば良いということだ。

めんどくさい！ 今までGo経由でしかやっていなかったので気にしたこともなかったわ。  
それにそもそも、CAとかそういうのってあんまり覚えてなかったりする。。。

### getinfo

クライアントように`ca.pem`を作るやり方もClaudeさんにやってもらった。
dockerで"lnd2"という名前にしたのでそのままにしている。

本番運用であれば、`ca.pem`と`ca.key`は作り直さないようにしておくとクライアント側に再配布しなくて済む。

```bash
cd ~/.lnd

# CA(自己署名、CA:TRUE)
openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:prime256v1 \
  -nodes -days 3650 -keyout ca.key -out ca.pem \
  -subj "/O=lnd-test-ca" \
  -addext "basicConstraints=critical,CA:TRUE" \
  -addext "keyUsage=critical,keyCertSign,cRLSign"

# サーバ証明書(CA:FALSE)のCSR
openssl req -newkey ec -pkeyopt ec_paramgen_curve:prime256v1 \
  -nodes -keyout tls.key -out server.csr \
  -subj "/O=lnd"

# CAで署名
openssl x509 -req -in server.csr -CA ca.pem -CAkey ca.key -CAcreateserial \
  -days 3650 -out tls.cert \
  -extfile <(printf "subjectAltName=DNS:localhost,DNS:lnd2,IP:127.0.0.1\nbasicConstraints=critical,CA:FALSE\nkeyUsage=critical,digitalSignature,keyEncipherment\nextendedKeyUsage=serverAuth")

chmod 600 tls.key
```

`Cargo.toml`

```toml
[dependencies]
tokio = { version = "1.53.2", features = ["full"] }
voltage-tonic-lnd = "0.5.0"
```

`main.rs`は[get_info.rs](https://github.com/voltagecloud/tonic_lnd/blob/c39cefc6f05d41a21504625e0db7a0b3f69daad6/examples/get_info.rs)ほぼそのまま。
ファイルの順番がどっちがどっちかわからなくなったので両方指定させるようにしたくらいか。

元は`tls.cert`を与えるようになっていたけど、こちらはクライアントアプリなので`ca.pem`の方を与える。

```rust
use voltage_tonic_lnd::Client;

#[tokio::main]
async fn main() {
    let mut args = std::env::args_os();
    if args.len() != 4 {
        eprintln!("Usage: cargo run -- <URL> <CA_file> <macaroon_file>");
        eprintln!("\n  ex.: cargo run -- https://127.0.0.1:10009 ~/.lnd/ca.pem ~/.lnd/data/chain/bitcoin/regtest/admin.macaroon");
        return;
    }
    args.next().expect("not even zeroth arg given");

    let address = args
        .next()
        .expect("missing arguments: address, cert file, macaroon file");
    let ca_file = args.next().expect("missing arguments: macaroon file");
    let macaroon_file = args
        .next()
        .expect("missing arguments: cert file and macaroon file");
    println!("macaroon: {:?}", macaroon_file);
    println!("ca_file: {:?}", ca_file);

    let address = address.into_string().expect("address is not UTF-8");
    let mut client = Client::builder()
        .address(address)
        .macaroon_path(macaroon_file)
        .cert_path(ca_file)
        .build()
        .await
        .expect("failed to build client");

    let info = client
        .lightning()
        .get_info(voltage_tonic_lnd::lnrpc::GetInfoRequest {})
        .await
        .expect("failed to get info");
    println!("{info:#?}");
}
```

## Nigiriのtls.certを変更する

Nigiriで立ち上げたlndにやりたい場合も同じようにやればよい。

```shell
nigiri stop
cd ~/.nigiri/volumes/lnd

```

Claudeさんが既存のファイルを使いそうな手順を示してくれたので一応書いておくが、私は試していない。
どうせなければ作る程度のファイルなのだから、前述した手順で良いと思うのだ。

```bash
# LND生成のものをCAとして退避
mv tls.cert ca.pem
mv tls.key  ca.key

# サーバ用の鍵とCSRを新規作成
openssl req -newkey ec -pkeyopt ec_paramgen_curve:prime256v1 \
  -nodes -keyout tls.key -out server.csr -subj "/O=lnd"

# LND生成のCAで署名(CA:FALSE のサーバ証明書)
openssl x509 -req -in server.csr -CA ca.pem -CAkey ca.key -CAcreateserial \
  -days 3650 -out tls.cert \
  -extfile <(printf "subjectAltName=DNS:localhost,DNS:lnd,DNS:lnd2,IP:127.0.0.1\nbasicConstraints=critical,CA:FALSE\nkeyUsage=critical,digitalSignature,keyEncipherment\nextendedKeyUsage=serverAuth")

chmod 600 tls.key
```
