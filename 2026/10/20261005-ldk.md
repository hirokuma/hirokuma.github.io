## 動かす

今回も[Nigiri](https://github.com/vulpemventures/nigiri)を使った。

```bash
nigiri start --ln
```

Nigiriの`rpcuser`と`rpcpassword`を指定し、ポート番号は`9735`を使われているので適当に指定。
コマンド入力待ちになる。

```shell
$ cargo run admin1:123@127.0.0.1:18443 ./data 19735 regtest
LDK startup successful. Enter "help" to view available commands. Press Ctrl-D to quit.
LDK logs are available at <your-supplied-ldk-data-dir-path>/.ldk/logs
Local Node ID is 03f900458e1919d89622f29c993b961656b81bdeea196554ab440300e5ec8ec9e8.
>
```

`connectpeer`をしてみよう。  
まずはNigiriの方のLNDノードを知る。

```shell
$ nigiri lnd getinfo | jq .identity_pubkey | jq
"02b60165f044978996617c33d3978e9f2c39c3fe09721e0111ee4fa7332b68528b"
```

ldk-sample側に打ち込む。

```log
> connectpeer 02b60165f044978996617c33d3978e9f2c39c3fe09721e0111ee4fa7332b68528b@127.0.0.1:9735
SUCCESS: connected to peer 02b60165f044978996617c33d3978e9f2c39c3fe09721e0111ee4fa7332b68528b
```

Nigiri側で`listpeers`すると、ldk-sampleの開始時に出力されたnode_idと一致していることがわかる。

```shell
$ nigiri lnd listpeers | jq .peers[0].pub_key
"03f900458e1919d89622f29c993b961656b81bdeea196554ab440300e5ec8ec9e8"
```

## 気づいたこと

### keyseedは素のデータか

最初にウォレットというかノードというかの鍵データを作りに行くのだが、乱数で埋めた後で`Write::write_all()`しているだけのように見える。
パスフレーズなどの入力もなかったし、素のデータを保存しているのだろう。

最近のldk-nodeでは[from_bip39_mnemonic](https://github.com/lightningdevkit/ldk-node/blob/144a1581c933bba1504f6adca59e03e5e5e15e08/src/entropy.rs#L74)を使うようで、
ニモニックとパスフレーズを使い、最終的には[bip39](https://docs.rs/bip39/latest/src/bip39/pbkdf2.rs.html#99)の`pbkdf2::pbkdf2()`でPBKDF2-HMAC-SHA512になっているようだ。
下手に自分で実装するよりは使ったほうがよさそう。

ドキュメントを見るとデフォルトの[Private Key Management](https://lightningdevkit.org/introduction/private_key_management#private-key-management)があるそうなので、
そちらを使うのも良いかもしれない。

### パラメータがたいへん

[feesの設定](https://git.rust-bitcoin.org/hirokuma/ldk-sample/src/commit/47c93ef3e7902f9ddfec757293ff9ca29227c4d1/src/bitcoind_client.rs#L86-L100)を見るとだいたい固定値になっている。
[Initialize the FeeEstimator](https://lightningdevkit.org/building-a-node-with-ldk/setting-up-a-channel-manager#initialize-the-feeestimator)にあったので気づいた。

fee_estimatorだけでなく`ChannelManager`の初期化には[Adding a ChannelManager](https://lightningdevkit.org/building-a-node-with-ldk/setting-up-a-channel-manager#adding-a-channelmanager)にあるパラメータが必要だ。
[ldk-sampleの場合](https://git.rust-bitcoin.org/hirokuma/ldk-sample/src/commit/47c93ef3e7902f9ddfec757293ff9ca29227c4d1/src/main.rs#L775-L788)でも用意がいる。  
デフォルト値でよいところもあるだろうが、デフォルト値でよいのかどうかは難しい。
LNDやCore-Lightningを参考にするにしつつがんばる、くらいか。

### minimum_depthはどこよ

チャネルオープン時、funding transactionを展開してからある程度confirmationが進んでからチャネルオープンが完了になる。
その「ある程度」は[accept_channelメッセージ](https://github.com/lightning/bolts/blob/1aadb719b4007c4cea0ba6e36b08c4fb53788dee/02-peer-protocol.md#the-accept_channel-message)の`minimum_depth`が基準となる。
funding transactionを待つ方のノードが送信するメッセージで、`minimum_depth`以上confirmationが進んだらfunding transactionは安定したものとみなして`channel_ready`を交換する。  
特に取り決めはなく、小さくすれば早くチャネルはオープンするがreorgなどのリスクを負うことになる。

その設定がどうなっているかというと、ldk-nodeではデフォルト値になっているとのこと。
[minimum_depth](https://docs.rs/lightning/0.2.7/lightning/util/config/struct.ChannelHandshakeConfig.html#structfield.minimum_depth)のデフォルト値は`6`だ。なかなか長い。  
[ldk-sample](https://git.rust-bitcoin.org/hirokuma/ldk-sample/src/commit/47c93ef3e7902f9ddfec757293ff9ca29227c4d1/src/cli.rs#L661-L665)もデフォルト値のようなので同じだ。

[前回](https://blog.hirokuma.work/2026/10/20261002-ldk.html)は`generatetoaddress 3`と3 confしかさせていないが、あれはldk-nodeアプリはfunderでLND側が`minimum_depth`を決める立場だからだ。
LNDはfundingする額によって値が変わり、小さいと`3`、大きいと`6`までの範囲で増えていたような気がする。
