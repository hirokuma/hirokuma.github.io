EIP-7702を使っているシステムが攻撃されて資金流出したというニュースがあった。  
調べておこう。

## delegate EOA

せっかく日本語で書いてあるのでリンクを載せよう。

* [Pectra EIP-7702 guidelines - ethereum.org](https://ethereum.org/ja/roadmap/pectra/7702/)

[Pectra](https://ethereum.org/ja/roadmap/pectra/)は2025年5月のEthereumアップグレードである。
Ethereumは年に1回くらい大きなハードフォークが行われているようで、過去にはできなかった新しい機能が追加される。  
過去からの仕様変更ではないのでウォレットアプリだったりRPCを使うだけのアプリはそのままでもよいが、
新しい機能を使いたかったり検証が必要だったりすると対応が必要、というのはどこも変わらない話だ。

このとき追加された機能の1つが[EIP-7702](https://eips.ethereum.org/EIPS/eip-7702)だ。
トランザクションタイプとして`4`が追加さた。

### Transaction Type 4

私がEthereumトランザクションの構造を調べたのはThe Mergeよりもかなり前で、タイプとしては`2`の時代だ。

| Type | EIP |
| ---- | ---- |
| 2 | EIP-1559 |
| 3 | EIP-4844 |
| 4 | EIP-7702 |

これは、今はType-4しか受け付けない、というわけではない。
Type-2が基本で、それに追加のパラメータが使えるという感じだ。

### 委任

Ethereumでは、秘密鍵から作ったアカウントをEOAと呼ぶ。
そうではなくスマートコントラクトのアドレスはコントラクトアドレスと呼ぶ、のだと思う。自信ない。
BitcoinはUTXOモデル、Ethereumはアカウントモデル。秘密鍵を使った操作はアカウントに紐づく。

EIP-7702はEOAに、このEOAの操作は秘密鍵ではなくコントラクトアドレスの方を使います、という「設定」を行う。
なのでEOAを扱うような気持ちで処理をしても実際には設定先のコントラクトアドレスが実行されるようになる。
変更はできるが、一時的なものではない。

最初に説明を読んだときは「？？？」だった。  
もちろん設定するにはEOAの署名がいるのだけど、こんなの何に使うんだと思った。  
使い道は、たとえばマルチシグウォレットにする、などだ。
Bitcoinの場合はマルチシグを扱うのはそんなに難しくないが、Ethereumの場合はスマートコントラクトを作らないといけない。
作ってしまえばよいのだが、EOAを扱うのとは勝手が違いすぎて面倒だと思う。
「設定」されるので自動的にEOAの処理をしているのがスマートコントラクトになるので敷居が下がる。  
そういう設定をしたアカウントは"Smart Contract Account"(SCA)とか"Smart Account"(SA)とか呼ばれたりする。

[ガイド](https://ethereum.org/ja/roadmap/pectra/7702/)に出てくる「Safeにデリゲート」の"[Safe](https://safe.global/)"はそういうコントラクトを展開している企業の1つだ。
たぶん企業だと思う。[リポジトリ](https://github.com/safe-fndn/safe-smart-account)もある。  
Safe以外にもある。

### EIP-4337

EIP-7702よりも前にEIP-4337というものが出ている。  
新たにマルチシグウォレットを作るならEIP-4337だけで運用できるのだが、既存アカウントを使いたいならEIP-7702と併用するとよし、みたいな感じだ。
EIP-7720の話をするとセットで出てきやすい。

まず、[Account Abstraction](https://ethereum.org/ja/roadmap/account-abstraction/)という構想がある。通称AA。  
アカウントを抽象化して自由度を高めよう、みたいな話だと思う。すまん、よくわかってない。

この思想をそのままEthereumで動かそうとするとプロトコルレベルで大きな変更をしないといけないので難しい、
じゃあ今できる範囲で一部だけでもやってみよう、ということで最初に出てきたのがEIP-4337、だと思う。  
なので、Account Abstraction == EIP-4337とかEIP7702とかではない。

ものすごく大雑把に言えば、共通してみんなが使える EntryPoint というスマートコントラクトをデプロイしていて、
そのコントラクト経由で別のコントラクトを実行するというものだ。  
ああ、たぶん言葉語りていない・・・。  
コントラクトを呼び出すトリガはEOAからしかできないので、会社などで運用したくてもEOAを1つは用意しないといけない。
が、それはやっぱり怖い・・・みたいなときに使いやすい。

EntryPointはこれを書いている時点で[v0.9.0](https://github.com/eth-infinitism/account-abstraction/releases/tag/v0.9.0)までデプロイされている。
ローカルで動かしたかったらREADMEにあるようにcloneしてyarnするのがよいんじゃないかな。

## 一時的ではない

最初にこれを調べようと思ったのも、ERC-20だけ持っていてETHを持っていなかい人はどうするんだろう？という疑問からだった。
コントラクト関数をsendで呼び出すにはトランザクションが必要で、いわゆるガス代が必要になる。
ガス代はEVMのネイティブトークンなのでEthereumならETHになる。  
世の中ではUSDTやUSDCをお金代わりに使ったりできるようだけど、そもそもETH持っていないといかんけどない人もいるんじゃなかろうかと思ったのだ。  
取引所によってはEIP-7702/4337を登録しているようだったらガス代の代わりに使いたいトークンから手数料を持っていく(ガス代やEIP-4337のpaymasterが払う)というしくみがあるということだった。

そういうのは一時的な設定だろうと思ったのだが、現在のEIP-4337では登録が残るタイプになったそうだ(案では一時的なものにするというのもあったらしい)。
まあ、Smart Accountという扱い方をするなら一時的なものもねぇ、ということなのか。  
最近AIコーディングで、はいはい、とあまり読まずに進めてしまう自分であったが、ある程度リズムよくできてしまう作業というのはリズムが崩れない限りは見直さないところがあると思う。
そうあるのは私だけではないと思いたい。。。

もし自分のEOAがSmart Accountになっている場合は事前に設定を確認する、なっていない場合もなっていないことを確認する、みたいなのが自動で入っていないといかんな。
あー、でもハッキングとかでアプリがやられていたら、その確認しました報告も怪しいものだ。
侵害されていないルートでチェックできるようにしないといかんけど、侵害されていないルートがわかるなら最初からそこでやればいいやん、になってしまい。。。

セキュリティ対策はシステムで考えるべき、という基本に立ち返るべきだが、それがそもそも難しいな。
