## LDKとは具体的にどれを指すのか

LDKはLightning Dev Kitの略だ。BitcoinのBDKと関係があったような気がするがよく知らない。

* [Lightning Dev Kit Documentation](https://lightningdevkit.org/)

ひとことで"LDK"と呼んではいるのだが、単独でそういうリポジトリがあるわけではない。  
BDKは「とりあえず`bdk_wallet`を使っておくか」とできたので楽だったのだが、LDKは具体的にどれがどうなっているのか知らないといかん。

[GitHub Organization](https://github.com/lightningdevkit)のREADMEは更新が2024年2月なのでPinnedで留めてあるリポジトリも変更されていないかもしれない。  
ドキュメントでは[ldk-sample](https://github.com/lightningdevkit/ldk-sample)がサンプル実装と書いてあるのだが、2026年8月にArchivedになったばかりだ。
最終更新も2026年2月と多少前で`Cargo.toml`もその頃の最新くらいで止まっているだろう。
そういう点では[TheBlueMatt氏版](https://github.com/TheBlueMatt/ldk-sample)を参照したほうが良さそうだ(TheBlueMatt氏は界隈で有名な人だ)。。。
とやってみたが今の時点(2026/10/04)では`Cargo.toml`でいくつかそんなバージョンないよというエラーでコンパイルできなかった。

ともかくどちらのリポジトリでも`Cargo.toml`で"lightning"がついたクレートをこれだけ使っている。
ldk-sampleのコードは見ていないのだが、わざわざ`Cargo.toml`に書いてあるということは実装しないと使えないはずなので、大変面倒そうだ。

これらはすべて[rust-lightning](https://github.com/lightningdevkit/rust-lightning)にある。
おそらくBitcoinの`rust-bitcoin`のような立ち位置だと思うが、Lightning Networkの複雑さからすると`rust-bitcoin`よりも単体で使うのは難しそうな気はする。

となると手軽に使えるのは[ldk-node](https://github.com/lightningdevkit/ldk-node)だろうか。
これ自体はライブラリとして使うもので、いろいろ引っ付いている。
それにv1.0になるまでAPIは安定しないと書いてある。実際、今の最新リリースv0.7.0を使ったサンプルコードをldk-nodeだけv0.8.0にするとコンパイルでエラーになる。  
それはわかっているのだが、ldk-sampleレベルまでAPI知識を持ち上げるのに時間がかかるので、まずはldk-nodeを使ってみよう。

それとは別の話として、TwitterのLightning Dev KitチームがLDKのバージョンとして挙げた名前は[rust-lightningのtags](https://github.com/lightningdevkit/rust-lightning/tags)のようだ。
なので公式？としては LDK=rust-lightning ということかもしれない。  
なお、ldk-sample(4d9ae57)とldk-node(v0.7.0)はlightning="0.2.0"だったので、上げられるなら"0.2.7"まで上げたほうがよいかもしれない。

## ldk-node

### add

コレを書いている時点ではv0.7.0が最新である。

```bash
cargo add lnd-node
```

開発中のものを使いたければこうか。
いまの時点ではv0.8.0開発中である。bdk_walletがv3系になっているので、前回のリリースから10ヶ月以上経っている今はどうすべきか悩ましい。
v0.8.0のRC版は近々登場しそうな気配ではある。

```bash
cargo add --git https://github.com/lightningdevkit/ldk-node ldk-node
```

### DBファイル名やテーブル名は固定

ldk-nodeが管理するデータのディレクトリは指定できるのだが、ファイル名は`SQLITE_DB_FILE_NAME`などで固定されているので変更できない。
気に入らなければforkして変更すればよかろう。

* [ldk-node/src/io/sqlite_store/mod.rs at v0.7.0 · lightningdevkit/ldk-node](https://github.com/lightningdevkit/ldk-node/blob/v0.7.0/src/io/sqlite_store/mod.rs#L28-L36)

データディレクトリを設定しない場合はエラーにならずデフォルト値 `/tmp/ldk_node` が使われる。

* [ldk-node/src/config.rs at v0.7.0 · lightningdevkit/ldk-node](https://github.com/lightningdevkit/ldk-node/blob/v0.7.0/src/config.rs#L39)

データディレクトリにファイルがあると自動的に読み込む。カレントディレクトリに作られると思い込んでいると「何もないのにウォレットファイルを読んでる？？」と混乱するので注意しよう。

### デフォルト値

データディレクトリ以外にもデフォルト値がある。

* [Config in ldk_node::config - Rust](https://docs.rs/ldk-node/0.7.0/ldk_node/config/struct.Config.html#defaults)

`Builder::new()`を使うとこのデフォルト値が使われる。`Builder::from_config()`で指定した`Config`を使うこともできるし、`Builder`を変更するメソッドもあるのでお好みで。

### node_id@ip_addr:port はBOLT標準ではない

ノードの接続先を表すのに使う"node_id@ip_addr:port"というフォーマットがあるが、BOLT標準と思い込んでいたがそうではなかった。
ldk-nodeでパースできないかAIに聞いたが存在せず、愚痴っぽく「標準なのになんでないんだろうねぇ」と言ったら、そうではない、と。
確かに、BOLTでそういうのが必要なのはBOLT7くらいで、そこでもadvertiseするだけだから文字列としては必要ないのよね。うっかりうっかり。

Claudeさんはこういうコードを作ってくれた。

```rust
use std::str::FromStr;
use ldk_node::bitcoin::secp256k1::PublicKey;
use ldk_node::lightning::ln::msgs::SocketAddress;

fn parse_peer(s: &str) -> Result<(PublicKey, SocketAddress), String> {
    let (id, addr) = s.split_once('@').ok_or("'@' が見つかりません")?;
    let node_id = PublicKey::from_str(id).map_err(|e| e.to_string())?;
    let address = SocketAddress::from_str(addr).map_err(|e| format!("{:?}", e))?;
    Ok((node_id, address))
}

// 使用例
// let (node_id, addr) = parse_peer("02abc...@127.0.0.1:9735")?;
// node.connect(node_id, addr, true)?;
// node.open_channel(node_id, addr, 100_000, None, None)?;
```

## ldk-nodeはfulfill後のrevoke_and_ack交換まで待たない

LN送金後に終わるまで待つためイベントで[PaymentSuccessful](https://docs.rs/ldk-node/0.7.0/ldk_node/enum.Event.html#variant.PaymentSuccessful)を待っていた。
`PaymentSuccessful`を受け取ったらすぐに残高出力して終了するようなサンプルコードである。  
実際にそれでやったのだが、受け取る相手側のノードではまだ送金が完了していない状態になっていた。v0.7もv0.8もだ。

細かい話になるが、Lightning Networkでは安全に送金を行うため、送金するためのHTLCを追加する`update_add_htlc`を行う工程と、そのHTLCを片付ける工程に分かれている。  
正常な場合は後工程を`update_fulfill_htlc`というメッセージで行う。  
これでメッセージを送れば終わりというわけではなく、`update_add_htlc`の後に「相手がいなくなってもHTLCを解消できる手段」のトランザクションを交換しないと終わらない。
`update_fulfill_htlc`も同様で、HTLCがなくなった後の状態を表すトランザクションを交換して終わりになる。

送金側からすると、最短で送金したとみなすのは`update_add_htlc`を送ってトランザクションを交換した時点である。
理屈上はそれ以降は相手がいなくなってもHTLCを解消する手段があるからで、それなら送金したとみなしてもよかろう、というところだ。  
ただこの手段、Lightning NetworkではなくBitcoinのチェーンにトランザクションを展開しないといけない。
なのでBTCの手数料がかかる。それにそのチャネル自体も閉鎖しないといけない。  
つまり、その時点で送金完了できるというのはわかるんだけど、あまりその手段は取りたくないというところだ。

なぜそういう微妙なタイミングで終わりたい時があるかというと、どんどん送金したりしたい場合だ。
ここまで終わったんだから次の送金をやろう、みたいなときかな。  
こういうのは中継するLNノードなのか末端のLNノードなのかで意識が違うし、LNノード実装によっても違いが出てくるところだ。

lnd-nodeはどうかというと、`PaymentSuccessful`は`update_fulfill_htlc`を受信したタイミングで発生させているらしい(AI談)。
もうちょっと下側だとfuilfillが終わったときのイベントも発行していてldk-nodeは受け取っているのだが[捨てている](https://github.com/lightningdevkit/ldk-node/blob/144a1581c933bba1504f6adca59e03e5e5e15e08/src/event.rs#L1529)そうだ(AI談)。  
まあ、ldk-"node"だからさっさとpeerを切断するようなものじゃないし、そうせざるを得ないならイベントを上げても仕方ないやん、ということかもしれん。

じゃあどうしたかというと、今回は単純に`sleep`で待たせた。
きれいに取得できないなら時間待ちしてもいいのだ。2秒も待たせているが他に合わせただけで他意はない。
